Release Impact Radius

Before shipping a Jira version, the app walks everything attached to it — tickets, code, builds, services, teams, incidents, documentation — and returns a go / conditional go / no-go verdict in which every reason points at its proof.

The problem

Scattered

Jira knows the tickets, the VCS knows the PRs, JSM knows the incidents, Confluence knows the docs. Nobody joins them.

Decided in a meeting

The go/no-go is settled from memory in a room — often the morning of the ship.

Consequences are known

A neighbour team discovers the change in production, you ship over an open incident, support learns the news from a customer.

One verdict, three states

GO

No blocking nor major signal active. The coverage is stated, never hidden.

CONDITIONAL GO

At least one major signal or an active waiver — the conditions are listed, one by one.

NO-GO

At least one blocking signal without a waiver, ordered by severity, each with a clickable proof.

Signals — each answerable with a proof

The verdict is deterministic. Every signal shows four things: what is observed, why it matters, the link to the proof, and how to clear it.

CodeSignalDefault severity
COMP-01Unfinished ticket in the releaseBlocking
COMP-02Done ticket with no commit nor PRMajor
COMP-03Open pull request on a release ticketBlocking
QUAL-01Latest build failed on a release ticketBlocking
QUAL-02Pull request merged without approvalMajor
DEP-01Ticket blocked by a still-open ticketBlocking
DEP-02Cross-project ticket depends on this releaseMajor
EXP-01Open incident on an impacted serviceBlocking
EXP-02Incident resolved less than 7 days agoMajor
DOC-01Linked Confluence page not updated this cycleMinor

More signals are implemented (reopened bugs, late additions, deployment freezes, concurrent releases, risk zones learned from past 72 h outcomes) and are documented in the repository.

Built on Forge, with the Teamwork Graph, Rovo and MCP

Teamwork Graph

Ticket → commit → PR → build, teams and Compass components, read as the user and cached with the dossier.

Rovo agent

“Can we ship 2.4?” — the agent only restates decisions and links it never computes itself, from the same saved dossier as the screen.

MCP tools

Seven read-mostly tools: get-release-impact, list-release-signals, simulate-without, request-waiver… A code agent can ask whether its PR holds a release back.

No egress outside Atlassian: Forge SQL storage and the hosted LLM keep the data inside the product — an argument of trust the submission puts forward.

Proven against a real site

Deployed to development and production, installed on Jira and Confluence of a Forge demo site. A recompute triggered by a real Jira event ends with:

recompute finished {
  versionName: '2.4', verdict: 'no-go', confidence: 'low',
  signals: 3, codes: 'COMP-01,DEP-01,DEP-02', blocking: 2, major: 1,
  coverageCode: '0/14', coverageService: '2/14', narrativeFromModel: true
}

An acceptance harness replays four of the eight acceptance points of the spec against the live site: R1 no-go + proof R5 honest low coverage R6 auto recompute in 13 s R8 no hallucinated key. Low confidence and service coverage are stated, never dressed up — missing data is never presented as good news.
